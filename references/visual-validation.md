# 视觉验证闭环

本规则仅在完成 UI 实现后按需加载，用于把代码检查扩展为基于真实渲染结果的视觉验证。它描述能力和结果，不绑定特定浏览器、自动化框架或 Agent 平台。

## 一、适用条件

目标项目存在可运行、可渲染的页面或组件，且当前环境具备访问界面与采集截图的能力时，必须执行完整闭环。

以下情况采用能力感知降级：

- 项目没有可用的运行或预览入口
- 当前环境无法访问渲染结果或采集截图
- 完成截图需要新增依赖、改变项目技术体系或获得额外权限
- 与本次修改无关的既有故障阻止界面启动

降级时仍需执行可以完成的构建、类型、Lint、测试、资源路径和 Theme 一致性检查，并明确记录视觉验证未完成的原因。不得声称视觉闭环已经通过。

## 二、建立验证矩阵

截图前先从用户需求、Phase 1 的项目约束和 Phase 4 的 UI 方案中提取验证矩阵：

- **主视口**：至少覆盖任务的主要使用环境
- **响应式视口**：需求明确涉及响应式时，覆盖项目既有断点或需求指定的代表性断点
- **关键状态**：只覆盖本次需求涉及且能够安全复现的默认、loading、empty、error、disabled、展开、选中、hover、focus 等状态
- **关键路径**：多页面或多步骤任务覆盖核心用户路径，不对无关页面做全量截图

优先复用项目已有的预览入口、测试数据、Story、fixture 或 mock。不得为了制造截图状态修改生产数据、调用高风险外部操作或扩大用户授权范围。

## 三、单轮验证流程

每个验证轮次依次执行：

1. **实现检查**：运行与变更范围相称的构建、类型检查、Lint 和测试；影响渲染的失败应先修复
2. **运行界面**：启动或复用项目现有预览环境，打开目标页面或组件
3. **等待稳定**：确认字体、图片、异步内容和必要动效已进入可评估状态，避免把加载过程误判为缺陷
4. **采集截图**：按照验证矩阵采集当前轮次的真实渲染结果
5. **视觉评估**：逐项检查需求符合度、Theme 一致性和界面质量，并为问题分级
6. **修改与复验**：存在阻断或主要问题且仍有剩余轮次时，只修改任务范围内的代码；下一轮重新执行受影响检查并采集新截图，不得复用旧截图作为通过证据

每轮必须基于实际观察结果决定是否继续，不能预设一定需要用满三轮。

## 四、评估维度

按以下维度检查截图和可观察状态：

- **需求与信息层级**：核心任务、内容顺序、主次操作和关键状态是否符合需求
- **布局与空间**：对齐、间距、尺寸、密度、折行、遮挡、裁切和滚动是否合理
- **视觉语义**：颜色、字体、圆角、阴影、动效是否使用正确的 Theme Token，是否符合 standards
- **Pattern 与资产**：Pattern 的结构意图是否保留，图标、插图和资源路径是否正确
- **响应式表现**：目标断点下是否出现溢出、错位、不可读内容或不可操作控件
- **交互与可访问性**：需求涉及的 hover、focus、disabled 等状态是否可辨识，文本对比度、键盘焦点和语义结构是否存在明显问题

视觉验证不是逐像素复刻。Theme 示例或 Pattern 仅作为设计依据；用户要求和目标项目约束优先。

## 五、问题分级与通过条件

每个问题至少记录严重程度、位置或状态、观察结果、预期结果和拟采取的修复。

- **阻断问题**：页面无法使用、崩溃、空白、核心内容不可见或核心任务无法完成
- **主要问题**：明显破坏布局、响应式、可访问性、Theme 一致性或关键状态，但页面仍可基本使用
- **次要问题**：不影响核心任务的局部视觉润色或低影响偏差

通过条件：当前轮次不存在阻断和主要问题。次要问题不阻止交付，但必须在最终说明中列出。

## 六、轮次与停止条件

- 最多执行 3 个完整的“运行 → 截图 → 评估”轮次
- 某轮通过后立即停止，不为消耗轮次而继续修改
- 第 1 或第 2 轮未通过时，在任务范围内修复后进入下一轮
- 第 3 轮仍有阻断或主要问题时，停止自动修改并交付问题清单、已尝试修复和建议下一步
- 若继续修复需要扩大范围、引入依赖、变更技术体系、执行高风险操作或获得新权限，立即停止并请求用户决策，不因尚有剩余轮次而越权

## 七、交付记录

最终说明应包含：

- 实际运行的检查和预览方式
- 截图覆盖的视口、状态与核心路径
- 完成的验证轮次及每轮主要结论
- 已修复的阻断和主要问题
- 遗留的次要问题
- 因能力或环境限制未完成的验证及其风险

截图文件默认作为临时验证证据，不提交到目标项目；只有用户明确要求保留时才纳入交付物。
