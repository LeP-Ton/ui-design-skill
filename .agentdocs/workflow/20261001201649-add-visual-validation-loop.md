# UI Design Skill V2.1 视觉验证闭环

## 背景与目标

- 原正式工作流以代码生成为终点，只要求运行相称检查，没有形成真实渲染结果驱动的自修正闭环。
- V2.0 候选版已拆分项目分析、代码实现与验证阶段，但仍缺少截图、问题分级、修改回跳和停止条件。
- 本次将 V2.1 发布为正式入口，使 UI 任务在能力允许时执行“运行、截图、评估、修改、再评估”。

## 约束与原则

- 保持 Theme 插件化、平台无关、手动调用和渐进式披露。
- 不绑定特定浏览器、截图工具、自动化框架或 Agent 平台。
- 不为截图擅自新增依赖、改变目标项目技术体系或扩大用户授权范围。
- 最多执行 3 个完整验证轮次，避免无上限重试。
- 无阻断和主要问题时通过；次要问题允许保留但必须说明。
- 环境不具备预览或截图能力时执行能力感知降级，不得虚报视觉验证通过。

## 关键风险

- 真实视觉闭环依赖目标项目具有可运行界面，并依赖执行环境具备访问和截图能力。
- 视觉评估存在一定主观性，因此以问题严重程度和可观察现象为依据，不引入伪精确评分。
- 简单 UI 任务需要额外的运行与截图成本，但通过需求驱动矩阵控制验证范围。
- 三轮后仍未收敛的任务需要用户进一步决策，不能继续无限自动修改。

## 关键实现说明

- 每个验证轮次必须使用当前代码产生的新截图，旧截图不能作为修改后的通过证据。
- 截图覆盖范围由需求、项目断点和关键状态决定，不强制所有任务使用固定分辨率。
- 当前轮次不存在阻断和主要问题即通过；次要问题记录后可以交付。
- 第 3 轮仍有阻断或主要问题时停止自动修改，并说明剩余问题、已尝试修复和建议下一步。
- 无截图能力时仍执行可完成的代码与 Theme 检查，但交付状态必须标记为“视觉验证未完成”。
